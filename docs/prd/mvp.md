# 项目管理与运维平台需求

`dev-ops` 面向内部团队，以关联 Git 仓库的项目为工作入口，集中管理需求、客户 Bug、PR 和运维交付信息。代码保留在 GitHub 或 Gitea，平台展示代码上下文和业务进度。团队以本地开发为主，平台协助成员了解谁在推进需求、开发进行到哪里，以及有哪些可用产物和已发布版本。

**提测是业务状态，项目流水线由研发自行配置，平台只收集最终构建产物和交付结果。两者独立运行。** 具体边界以第 6 章为准。

本文用于产品、研发和测试对齐 MVP 需求，不代表功能已实现。第 1 至第 10 章记录产品范围；第 11 章区分已确定的接入方案与待确认建议，第 12 章集中记录待定事项。设计图和交互原型中的示例状态、人员及数据不构成额外业务约定。

## 1. 产品定位与范围

第一版服务内部团队，支持多人和 AI Agent 协作。Multica 是产品方向的参考，页面交互和项目管理流程按本文定义，不以复刻其功能为目标。

管理对象覆盖 Web、后端服务、小程序和移动端应用。研发主要在本地使用 Codex、Claude 等工具完成开发，平台不要求将开发过程迁入在线编辑器，也不要求将 PRD 交由 Agent 执行。

既有产品约定为“以项目为核心，一切皆文件”，管理 PR、Issue 和 Git 仓库，并允许各项目配置自定义 Bot。Bot 使用 pi 作为 Agent 执行循环；文件理念的具体范围和 pi 集成方式仍需细化。

第一版 Bot 的业务范围是项目与运维辅助，直接通过 `@bot` 自动开发属于后续扩展方向。本文不规定数据库结构、接口协议或流水线执行架构；工程规范见 [AGENTS.md](../../AGENTS.md)，技术方案另见[后端选型规划](../../server/docs/architecture.md)。

## 2. 成员与权限

平台采用两个权限角色，开发者默认拥有全部管理权限，不增加按项目、服务或环境划分的权限矩阵。

| 角色 | 权限 | 说明 |
| --- | --- | --- |
| 开发者 | 全部管理权限 | 可维护项目、需求、Bug、交付信息及平台配置 |
| 浏览者 | 只读 | 查看信息，不执行修改操作 |

产品、研发、测试表示业务职责，不是额外的权限角色。流程中的负责人和人工放行要求用于明确工作责任，不构成独立的审批角色体系。

客户提交 Bug 的入口属于单独的外部反馈渠道，不因此授予客户内部开发者权限。客户身份及可见范围列入第 12 章。

## 3. 导航与项目需求页

首页展示项目列表，提供项目状态、负责人、事项完成度、未完成需求与 Bug、待审 PR 和项目 Bots 数量。支持按名称检索与按项目状态筛选；统计入口进入相应模块。项目状态由成员维护，事项完成度从事项记录计算，不根据 PR 合并自动推断。

一级导航为“项目”“Bot”“Skills”，底部提供设置及成员入口。“仓库”与“项目”合并为“项目”，不单列“我的工作台”，侧栏不再重复展示仓库树和项目分组。成员通过项目入口选择项目，进入项目后默认展示需求列表。

项目页签顺序为 `bots → 需求 → 代码 → Bug → PR → 产物与版本`。`bots` 排在最前，默认选中“需求”；不设置“概览”和独立“上下文”页签。项目标题区保留项目选择、仓库路径及必要操作，不叠加项目说明副标题。

| 页面 | 主要内容 | 主要操作 |
| --- | --- | --- |
| 需求 | PRD 标题、负责人、业务进度、代码关联 | 搜索、按状态与负责人筛选、新建需求、打开详情 |
| 代码 | 已授权仓库的分支、目录、文件与提交 | 切换仓库或分支、查看文件及提交，在原平台打开 |
| Bug | 内部及客户问题、处理负责人、修复与回归进度 | 新建、筛选、讨论，查看关联 Issue 与 PR |
| PR | 关联仓库中的 PR、作者、源分支、目标分支及评审信息 | 查看列表、变更文件和详情，在原平台打开 |
| 产物与版本 | 服务的最新构建产物、测试及生产环境运行版本 | 下载或查看产物、访问测试环境 |
| bots | 项目智能体名册、独立对话、引用资源、技能调用与结果 | 用 `@` 选择仓库、文件、PR、事项或 Skill，在同一对话内协作 |

点击需求或 Bug 后，在右侧展开详情并保留列表、搜索及筛选条件。详情展示正文、负责人、状态、代码关联、讨论与活动。关闭详情返回原列表；修改只作用于同一业务记录。筛选无结果时显示空状态并允许清除条件；请求失败时显示错误及重试入口。

项目 `bots` 以对话为主体，不展示助手卡片和仓库提交摘要栏。一级 Bot 用于团队 Bot 管理，项目 `bots` 用于项目内使用，两者职责不重复。个人汇总待办与独立待办的入口及 MVP 保留范围列入第 12 章，不以已删除的工作台入口作为验收要求。

界面只保留操作、业务内容及必要反馈，不展示宣传语、重复来源标签、列表操作说明和常驻技术说明。空状态、失败提示及只读权限提示仍需提供。演示性质集中在原型标识和说明文档中表达。

视觉采用 DeepSeek Harness 的中性浅色背景、细分隔线与蓝色强调。主要操作及活动态采用官方 `deepseek-500` 色值 `#4176E6`，侧栏 `#F9FAFB`、主内容 `#FFFFFF`、中性选中底 `#EBEEF2`。这些是本项目的映射目标；官方所有按钮并非统一使用蓝色。参考[主题源码](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-theme/src/styles/design-platform.css)和[样式规范](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/web-styling.md)，核对日期为 2026-11-06。

## 4. 项目、服务与代码关联

一个项目代表一个产品，可以关联多个 Git 仓库和多个服务，例如前端站点、API 和管理后台。界面入口合并不代表项目、仓库、服务必须一一对应；服务与仓库的具体映射规则列入第 12 章。

平台确定通过 API 接入 GitHub 与 Gitea 的已有仓库，两者均须支持公有和私有仓库。Git 托管由来源平台承担，本平台不内置 Git 托管引擎。创建平台项目只建立平台记录及关联，不自动创建、迁移、镜像或复制远端仓库。成员授权并选择仓库后，即可在平台内查看其代码、Issue 与 PR；私有仓库无需改为公开。

可关联的仓库必须处于连接的授权范围内，成员访问同时受第 2 章的平台角色及仓库关联约束。连接授权不等于向所有访问者公开私有代码，也不改变现有开发者与浏览者角色。浏览者保持只读，客户反馈入口不获得代码访问权限。授权失效、撤销或移除仓库访问权限后，平台应停止提供该仓库的受保护内容，包括缓存内容，并显示访问不可用及恢复授权入口。

代码查看不要求用户手动同步。后端按需获取目录和文件，可结合缓存与后台自动更新；全仓克隆不是阅读文件的前置条件。切换分支后必须读取对应版本，无法访问、文件不存在和请求失败不得伪装为空目录。当前原型按读取和关联展示代码与 PR；MVP 的远端写入范围仍待确认，见第 11、12 章。

开发过程采用“人工状态加 Git 关联”的方式：负责人维护业务进度，代码记录提供进展依据。代码提交、合并记录不替代成员对业务状态的维护。

项目页面应能查看 PRD 执行人和开发过程，并汇总服务的交付信息。服务可以独立交付，版本展示规则见第 8 章。

Git 托管平台是代码、提交、PR 及远端 Issue 原生信息的权威来源。平台维护 PRD、内部 Bug、业务流转及其代码关联。PR 合并、Issue 关闭不会自动标记测试通过或已发布。

## 5. PRD 与研发流程

PRD 同时支持在平台内编写和关联外部文档。产品指派研发主负责人，主负责人可以与多名研发协作；进入测试环节时指定测试负责人。

平台记录以下业务过程。表中的环节用于描述工作流，不是已经确定的状态枚举，也不表示每个环节都必须增加审批动作。

| 环节 | 主要参与者 | 需要记录的业务内容 |
| --- | --- | --- |
| 提出需求、指派研发 | 产品 | 需求内容、研发主负责人和协作人员 |
| 技术调查 | 研发 | 调查结论；简单需求可直接通过 |
| 开发 | 研发 | 开发进度、关联代码与讨论 |
| 自测、准备提测 | 研发 | 自测、单元测试情况，以及可供测试的交付信息 |
| 提测 | 研发 | 业务状态流转、测试负责人 |
| 测试 | 测试人员 | 按 PRD 验证功能，提出 Bug 清单 |
| 修复 | 研发 | 处理测试发现的问题，记录修复进度 |
| 回归测试 | 测试人员 | 验证修复结果，未通过的问题继续修复 |
| 正式交付 | 相关负责人员 | 人工放行后上线或提审，记录交付结果 |

研发自测时可以通过自行配置的流水线准备可安装测试包，或将服务部署到测试环境。平台在业务流程中记录提测，不负责通过该状态动作执行上述工作。

开发完成、测试通过和已发布是不同的业务结果；提交外部审核也不等于已经发布。具体完成判定及状态取值列入第 12 章。

## 6. 流水线与提测的独立边界

研发自行配置项目流水线，决定构建、部署步骤和触发方式。平台在这一边界内负责收集、归档展示最终产物及交付结果，不要求内置流水线编排或执行能力。

| 对象 | 职责归属 | 与其他流程的关系 |
| --- | --- | --- |
| PRD 与提测状态 | 产品、研发、测试维护业务过程 | 不负责触发、等待或重试流水线 |
| 项目流水线 | 研发自行配置 | 独立决定何时构建、部署和产生结果 |
| 产物收集与展示 | 平台 | 接收并展示可供使用的交付结果，不据此自动推进 PRD |

以下规则约束产品设计和后续实现：

- 点击“提测”只改变业务状态，不自动触发构建、上传或部署。
- 提测不以某条流水线执行完成为强制前提。
- 流水线成功或失败不自动修改 PRD 状态，也不自动生成提测动作。
- 不以“构建失败”为由自动回退 PRD，或要求通过修改 PRD 状态重试流水线。

开发可按项目需要配置自动构建或部署。正式发布的人工放行要求属于第 9 章的业务约束，不推导为平台必须提供执行器、发布按钮或流程门禁。

## 7. 构建产物与测试交付

测试人员最终需要拿到可使用的测试版本。平台集中收集和展示以下交付内容，使成员能够找到构建结果和测试入口。

| 类型 | 最终交付内容 | 使用方式 |
| --- | --- | --- |
| 移动端应用 | 可安装的测试包 | 下载并安装 |
| 小程序 | 测试二维码 | 扫码体验 |
| Web／后端 | 测试环境访问地址及交付信息 | 访问页面或验证接口 |

产物的生成、签名、上传和测试环境部署由研发自行配置的交付过程完成。平台不因展示二维码就承担小程序上传，不因收集访问地址就承担部署执行。

平台展示最新构建产物，并提供对应的版本信息。收集是否采用主动上报、拉取结果或其他方式，以及平台保存文件还是仅保存引用，均列入第 12 章。

## 8. 服务版本与交付结果

各服务分别展示运行版本，允许独立发布。成员应能按服务和环境了解当前上线版本，同时查看可用的构建产物。“产物与版本”页面不单独展示交付记录列表或发布放行卡片；保留产物与运行版本的来源信息，以便核对交付结果。

最新构建产物与环境正在运行的版本需要分开展示。构建完成不代表该产物已经部署，也不能用最新构建记录直接替代线上版本信息。

第一版不要求统一的产品发布版本来绑定所有服务。运行版本的权威来源、交付记录的采集方式和版本标识规则列入第 12 章。

## 9. Bug、发布与外部审核

客户和内部人员都可以提交 Bug，在项目内统一处理。测试人员可根据 PRD 提出 Bug 清单，研发记录修复过程，测试人员记录回归结果；回归未通过的问题继续修复。

Git 平台中的 Bug 通常由 Issue 及其分类表示，需要约定标签或类型映射。平台不能仅凭读取代码自动获得 Bug 清单。平台本地 Bug 与外部 Issue 的关联方案见第 11 章；客户反馈入口不要求客户取得代码仓库权限。外部 Issue 的开关状态与本平台的修复、回归状态分别展示，避免同名字段覆盖不同含义。

正式发布需要人工放行。平台需要记录相关交付结果，但放行动作的承载位置、执行系统及结果回传方式尚待确认，不据此定义平台直接操作生产环境。

小程序和移动端应用的外部提审属于第一版范围。成员使用研发交付的产物，在外部平台人工提交审核；本平台记录审核与实际发布结果。平台不自动向外部平台提交审核，审核状态如何维护或同步列入第 12 章。

## 10. Bot、团队 Skills 与协作模板

### 10.1 全局智能体与项目 bots

全局 Bot 是团队智能体管理入口，采用表格展示名称、职责、负责人、使用范围、可用状态、运行环境、模型及最近活跃时间。支持搜索、按负责人筛选、创建、编辑及全局启停；详情提供配置、关联项目及运行记录。Bot 具有持续身份，同一团队 Bot 可以加入多个项目；也可以创建仅在指定项目使用的 Bot。

项目 `bots` 采用左侧名册、右侧对话的布局。名册展示本项目加入的 Bot、头像、职责、状态与最近消息；支持从团队目录添加或新建项目专属 Bot。成员选择 Bot 后进入其在本项目的独立会话。从全局管理页打开对话时，先选择已关联的项目。

全局配置维护名称、头像、职责、负责人、运行环境、模型及允许使用的 Skills。项目配置维护启用状态、仓库读取权限、技能子集及项目补充约定，不覆盖全局职责。项目选用的 AGENTS.md 模板在项目配置中查看。有效技能必须同时满足团队启用、Bot 允许、项目允许及当前成员有权使用；项目配置不能扩大全局授权。

全局停用、项目停用和运行环境离线分别显示，不能用“在线”代替授权状态。停用后禁止新运行，保留历史。移出项目仅移除绑定，不删除团队 Bot；会话与运行记录按项目及 Bot 隔离。一次请求由一位 Bot 负责，MVP 不引入自主多智能体编排。

平台内自建 Bot，第一版辅助项目与运维工作。Bot 在授权范围内可以直接操作，无需将每次调用都设计成人工确认；具体操作清单必须符合第 6 章的流水线边界，目前仍待确认。

项目 `bots` 采用以对话为中心的交互：选择 Bot、输入消息、引用资源，并在同一对话内查看回复和调用信息。提供新对话及当前项目的对话历史入口。参考 [Grok Bot 的消息与协作方式](https://docs.x.ai/grok-bot/chat-and-collaboration)，借鉴对话和 `@` 引用，不将其全部功能纳入本平台范围。

关于仓库的引用与调用统一通过输入区的 `@` 完成，不在对话上方堆叠分支、提交、PR 操作栏。输入 `@` 后可搜索并选择已授权资源，区分仓库、文件、PR、事项、Bot 和 Skill。选择后保留可识别的资源标识，回复中可以展开核对实际使用的资源。候选项受当前项目和成员权限约束，不允许通过手工输入绕过资源权限。

原型使用 `@repo/team/dev-ops`、`@file/src/api.ts`、`@pr/42`、`@PRD-024`、`@小李` 和 `@skill/pr-review` 演示不同类型。完整标识协议、多仓库同名资源消歧及历史资源失效规则由技术设计确定。未知、无权限或已停用的引用必须有明确反馈，不静默调用其他资源。

成员仍可在 PRD、Bug 的讨论中 `@bot`。项目对话用于处理不属于单个事项的问题；若后续保留独立待办，未关联项目的待办不默认绑定某个项目。Bot 不因被提及而获得额外远端写权限，自动开发仍属于后续扩展方向。

### 10.2 团队 Skills 平台

Skills 是团队技能的统一目录与管理入口，采用技能市场式浏览方式。目录支持按名称、调用标识和分类检索；技能详情展示用途、版本、来源、指令内容和启用状态。团队成员可以发布、编辑、启用或停用技能，权限遵循第 2 章。

Bot 在全局配置与项目授权范围内使用该目录中的已启用技能。成员既可以在技能详情选择“在 bots 中使用”，也可以在对话输入区通过 `@` 搜索 Skill。两个入口引用同一份技能定义，不复制维护。停用技能应从新调用候选中移除；手工输入已停用的标识也不能继续调用。历史对话中的调用信息仍可用于追溯。

团队技能平台不等于必须接入公开第三方市场。第三方来源导入、版本更新、审查和分发方式仍待确认，当前原型以团队维护的技能为示例。

### 10.3 AGENTS.md 模板

Skills 中提供独立的 `AGENTS.md 模板` 目录，支持新建、编辑、创建副本、搜索、查看全文、复制正文、下载文件、复制预览链接，以及明确选择目标项目后选用模板。预览链接应呈现分享时的内容版本；原型使用同站点快照链接，公网发布、访问权限和撤回机制需另行确定。项目 bots 使用所选模板作为协作约定；同一团队的不同项目可以选用不同模板。模板选择不应直接写入或覆盖远端仓库中的 `AGENTS.md`。

上下文和技能沿用“团队共用，加项目专属”的组织方式。团队维护通用能力，项目补充自身资料和约定；不恢复独立“上下文”页签。模板与仓库已有规则的合并顺序、项目覆盖、版本锁定及生效时机列入第 12 章。原型展示模板选择及调用信息，不代表模型、执行器或远端文件写入已经接入。

## 11. 接入方案与待确认建议

### 11.1 GitHub 与 Gitea 适配

API 接入方式与私有仓库支持已确定，产品范围见第 4 章。第一版围绕仓库信息、分支、目录、文件、提交、Issue 与 PR 的读取和关联实现，远端写操作仍列入第 12 章。GitHub 与 Gitea 使用统一的页面交互，保留来源平台及实例标识，便于成员定位原始记录。

不同 Gitea 实例中的同名仓库或相同 Issue／PR 编号不得混淆。平台不承诺两边能力完全一致；不支持、无权限、请求失败和同步延迟需要明确展示，不能转换为空列表或成功状态。

CI/CD 接入遵守第 6 章。选择 API 接入不增加内置流水线编排、执行、手动触发或重跑要求，也不将两边 Actions 的配置视为完全兼容。产物与交付结果的采集方式仍按第 12 章确认。

认证方案、适配器职责、缓存与事件同步约束及官方能力依据统一维护在[技术选型第 4.1 节](../../server/docs/architecture.md#41-代码平台-api-接入)。本节确定的产品要求不代表真实连接已实现或通过验证。

### 11.2 Bug 与外部 Issue

建议平台维护客户与内部 Bug，并按需关联已有 Issue，后续再扩展从平台创建 Issue。GitHub／Gitea 原生标题、标签及关闭状态从来源读取，本平台的业务状态由本平台维护。若需要双向修改同一字段，必须先确定权威来源、冲突处理及重试规则；不默认启用全量双向同步。

这会增加关联管理成本，但能保留客户反馈入口及回归流程。仅使用远端 Issue 可减少本地业务数据，是否满足客户权限和测试流程要求仍需产品确认。

### 11.3 需求与产物关联

建议允许 PRD 或 Bug 关联已有产物，便于成员知道测试的是哪个版本，并在排查问题时追溯交付结果。这种关联应保持第 6 章的独立边界，不触发流水线执行。

关联是否存在、是否必填、是否固定到某次构建，以及是否引入独立测试轮次，都需要产品负责人确认。自动提测、构建失败重试、测试轮次及其通知规则不作为已确认功能。

## 13. 需求核对场景

以下是后续设计与实现的验收依据，不表示当前代码已通过对应功能测试。

- 一级导航只有项目、Bot、Skills 及底部设置、成员入口，不再显示独立仓库或我的工作台导航。
- 进入一个项目后默认显示需求，项目页签按第 3 章排列，bots 位于最前但不默认选中。
- 需求可按文字、状态和负责人组合筛选，空结果可恢复；点击事项打开右侧详情，关闭后保留筛选条件。
- 已授权的已有 GitHub 或 Gitea 仓库可以关联到项目，无需另建仓库或由成员手动同步；文件查看读取当前分支，错误可见且可重试。
- GitHub 与 Gitea 分别使用公有、私有仓库验证读取和关联；私有仓库保持私有，未授权仓库不能关联或读取。
- 撤销授权或移除仓库权限后，按确定的检测时限停止返回受保护内容，缓存不能绕过权限检查；恢复授权后可重试读取。
- 不同 Gitea 实例中的同名仓库、相同 Issue／PR 编号分别展示；不支持的能力与请求失败不会被展示为成功或空数据。
- 代码、PR 和远端 Issue 的读取不自动改变平台业务状态；本地 Bug 与远端 Issue 按确定的映射方案处理。
- 一个项目可以展示多个服务，各服务分别呈现环境运行版本和最新构建产物，两者不会混为同一个版本。
- 产品能够创建内置 PRD 或关联外部文档，并指定研发主负责人、协作人员；提测时可指定测试负责人。
- PRD 可记录第 5 章所述业务过程，测试人员可以提交 Bug，研发与测试可以记录修复、回归结果。
- 没有正在运行的流水线时仍可以改变提测状态；该操作不会创建构建或部署任务。
- 平台收集到新产物，或获知流水线失败时，不会自动变更 PRD 状态。
- 测试人员可以获取第 7 章对应类型的交付入口；正式发布和外部审核结果能够与构建完成分别表达。
- 客户和内部人员均有提交 Bug 的方式；开发者可管理平台，浏览者保持只读。
- 成员可以从事项讨论或项目对话中 `@bot`，其能力受已确认的操作范围约束。
- 全局 Bot 支持搜索、负责人筛选、配置、启停、加入项目及运行记录；项目 bots 展示独立名册与会话。项目限制不扩大全局授权，停用及离线状态阻止新运行。
- 项目 bots 不展示助手卡片和 Git 摘要栏；输入 `@` 可选择资源及团队技能，未知、失效或无权限的引用不会被执行。
- Skills 支持搜索、分类、查看定义及管理启用状态；技能库入口与 bots 引用同一技能定义。
- AGENTS.md 模板可预览并按项目选用，选择结果在项目 bots 中可见，不自动改写远端仓库。
- 产物与版本页面只展示产物及环境版本，不单列交付记录或发布放行卡片。
