# 项目管理与运维平台需求

`dev-ops` 面向内部团队，提供持续工作的 Bot 团队、项目管理和运维协作。成员与独立 Bot 对话，或建立跨项目群组，由 Leader 分派任务、汇总交付并发起发布计划。Bot 按需调用项目工具；平台关联需求、Bug、Git 记录、服务版本、记忆及环境配置。代码保留在 GitHub 或 Gitea，研发继续使用本地开发工具，平台通过交付结果衔接开发与运维。

**提测是业务状态，流水线由平台内置提供：定义以仓库内 YAML 文件维护，由平台注册的自托管执行节点运行。提测不会自动触发构建或部署，流水线结果也不会自动改变业务状态。** 具体边界以第 6 章为准。

本文用于产品、研发和测试对齐 MVP 需求，不代表功能已实现。第 1 至第 10 章记录产品范围；第 11 章区分已确定的接入方案与待确认建议，第 12 章集中记录待定事项。设计图和交互原型中的示例状态、人员及数据不构成额外业务约定。实现状态与版本顺序以[需求版本规划](release-plan.md)为准：截至 2026-11-10，V0.1、V0.2、V0.3 阶段 A 与 V0.4a 已交付；V0.4b 前置为下一版本，Bot 与运维后移，详见文末版本顺序调整补充。

## 1. 产品定位与范围

第一版服务内部团队，支持多人和 AI Agent 协作。Multica 是产品方向的参考，页面交互和项目管理流程按本文定义，不以复刻其功能为目标。

管理对象覆盖 Web、后端服务、小程序和移动端应用。研发主要在本地使用 Codex、Claude 等工具完成开发，平台不要求将开发过程迁入在线编辑器，也不要求将 PRD 交由 Agent 执行。

项目管理业务事实，Bot 保持持续身份，任务保存执行进展。平台负责记忆与任务交接，向 Codex、Claude、pi 等工具提供统一接口；具体执行循环的适配方式由技术设计确定。全天候工作由事件接入和定时调度驱动，不依赖一个永久增长的聊天上下文。

第一版围绕“发现问题、建立任务、接收开发结果、验收、形成运维计划、执行并验证”展开。Leader 可以分派和转交任务，暂不要求多个 Bot 无限制互相调度或由平台托管全部开发过程。本文不规定数据库结构、接口协议或流水线执行架构；工程规范见 [AGENTS.md](../../AGENTS.md)，技术方案另见[后端选型规划](../architecture/server-foundation.md)。

## 2. 成员与权限

团队内成员采用管理员、开发者与浏览者三个角色。平台级 root 账号的邀请职责见第 2.1 节，不作为第四个团队角色。Bot 的项目资源授权、环境配置授权及生产操作放行另行记录；成员拥有管理权限不代表所有 Bot 自动获得同等凭据。

| 角色 | 权限 | 说明 |
| --- | --- | --- |
| 管理员 | 团队管理及业务管理 | 管理团队资料、成员、邀请、角色与团队凭据，同时具备开发者权限；可输入本人密码查看任意凭据明文 |
| 开发者 | 业务管理 | 维护项目、需求、Bug、交付及 Bot 配置；可以提出团队凭据配置请求；对已授权凭据可输入本人密码查看明文 |
| 浏览者 | 只读 | 查看信息，不执行修改操作 |

产品、研发、测试表示业务职责，不是额外的权限角色。流程中的负责人和人工放行要求用于明确工作责任，不构成独立的审批角色体系。团队至少保留一位正常管理员；降级或停用最后一位管理员时阻止保存。邀请保存为待加入，接受后才成为正常成员；原型仅模拟加入，不发送邀请邮件。

客户提交 Bug 的入口属于单独的外部反馈渠道，不因此授予客户内部开发者权限。客户身份及可见范围列入第 12 章。

### 2.1 邮箱邀请与账号开通

V0.1 采用邮箱邀请体系。平台设有 root 账号，由 root 向指定邮箱邀请团队管理员，再由团队管理员向成员邮箱发送邀请。平台实际发送包含 token 链接的邀请邮件，收件人从邮件进入 Web 端完成加入流程。

首次受邀者打开有效邀请链接后设置密码，填写要求的个人资料，再加入对应团队并进入首页。资料包含用户名、头像等信息，具体必填项和头像设置方式仍待确定。已开通成员退出或更换设备后，使用邮箱和密码登录。

root 的初始化与登录恢复、团队创建及邀请归属、邀请有效期、重复邀请、密码找回和资料规则仍需细化。root 已明确的能力是邀请团队管理员，其他团队管理及资源访问权限不由该能力自动推导。确认记录及待定细节见 [V0.1 需求细化](v0.1.md#73-已确认决定)。原型仍只模拟邀请，不代表真实邮件、账号或登录已经接入。

## 3. 导航与项目工作区

默认首页为独立 Bot 会话，不要求先创建或选择项目。项目列表提供项目状态、负责人、事项完成度、未完成需求与 Bug、待审 PR 和项目 Bots 数量。支持按名称检索与按项目状态筛选；统计入口进入相应模块。项目状态由成员维护，事项完成度从事项记录计算，不根据 PR 合并自动推断。

一级导航顺序为“项目”“协作”“运维”“能力”“凭据库”，底部提供管理员团队管理、设置及成员入口。团队切换采用侧栏最底部的紧凑方形图标，仅在当前用户加入两个及以上团队时显示；选中描边只包围图标，不再另占团队名称区域。切换团队同时切换其会话、项目和凭据数据，不能仅替换页面标题。协作提供群组、直接会话和待处理任务；项目提供业务记录；运维展示服务、事件、值守规则和变更；能力集中管理智能体、Skills、AGENTS.md、记忆、连接与节点。“仓库”与“项目”合并为“项目”，不恢复重复的仓库树。

项目页签顺序为 `需求 → 协作 → 代码 → Bug → PR → 流水线 → 产物与版本 → 环境变量`。默认选中“需求”。协作按标签归集当前项目的聊天和 Bots 群组，直接展示原聊天记录；无匹配会话时展示空状态，不自动创建群组；原型内部保留 `bots` 路由键以兼容旧链接。不设置“概览”和独立“上下文”页签。项目标题区保留项目选择、仓库路径及必要操作，不叠加项目说明副标题。

| 页面 | 主要内容 | 主要操作 |
| --- | --- | --- |
| 需求 | PRD 标题、负责人、业务进度、代码关联 | 搜索、按状态与负责人筛选、新建需求、打开详情 |
| 代码 | 已授权仓库的分支、目录、文件与提交 | 切换仓库或分支、查看文件及提交，在原平台打开 |
| Bug | 内部及客户问题、处理负责人、修复与回归进度 | 新建、筛选、讨论，查看关联 Issue 与 PR |
| PR | 关联仓库中的 PR、作者、源分支、目标分支及评审信息 | 查看列表、变更文件和详情，在原平台打开 |
| 流水线 | 仓库内 YAML 定义的流水线、运行记录与步骤日志 | 授权后手动触发、查看状态、日志与产物，不自动修改业务状态 |
| 产物与版本 | 服务的最新构建产物、测试及生产环境运行版本 | 下载或查看产物、访问测试环境 |
| 协作 | 会话或其中任务的标签关联当前项目的聊天及 Bots 群组 | 切换已有会话、直接阅读聊天；不提供标签筛选、新建会话、发送消息或创建任务 |
| 环境变量 | 按环境隔离的变量、密钥和 Bot 授权 | 配置、轮换、撤销、处理任务配置请求及查看访问记录 |

点击需求或 Bug 后，在右侧展开详情并保留列表、搜索及筛选条件。详情展示正文、负责人、状态、代码关联、讨论与活动。关闭详情返回原列表；修改只作用于同一业务记录。筛选无结果时显示空状态并允许清除条件；请求失败时显示错误及重试入口。

全局协作与项目协作访问同一会话和任务，切换入口不复制记录。能力中的智能体页面管理独立定义、项目能力授权和执行环境。会话可以不引用项目，也可以引用多个项目；资源引用与标签归集分别维护。项目入口按标签关联的项目归集已有会话，不改变会话成员或资源授权。左侧展示相关聊天和 Bots 群组，右侧直接显示同一会话的记录；切换会话留在项目页面，不提供聊天输入、新建会话或“全部标签”筛选。待你处理集中展示待验收、等待配置及受阻任务；通知可以返回原任务。需求与 Bug 详情提供“交给 Bot 跟进”，有活动任务时进入已有任务。

界面只保留操作、业务内容及必要反馈，不展示宣传语、重复来源标签、列表操作说明和常驻技术说明。空状态、失败提示及只读权限提示仍需提供。演示性质集中在原型标识和说明文档中表达。

视觉采用 DeepSeek Harness 的中性浅色背景、细分隔线与蓝色强调。主要操作及活动态采用官方 `deepseek-500` 色值 `#4176E6`，侧栏 `#F9FAFB`、主内容 `#FFFFFF`、中性选中底 `#EBEEF2`。这些是本项目的映射目标；官方所有按钮并非统一使用蓝色。参考[主题源码](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-theme/src/styles/design-platform.css)和[样式规范](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/web-styling.md)，核对日期为 2026-11-06。

## 4. 项目、服务与代码关联

一个项目代表一个产品，可以关联多个 Git 仓库和多个服务，例如前端站点、API 和管理后台。界面入口合并不代表项目、仓库、服务必须一一对应；服务与仓库的具体映射规则列入第 12 章。

平台确定通过 API 接入 GitHub 与 Gitea 的已有仓库，两者均须支持公有和私有仓库。Git 托管由来源平台承担，本平台不内置 Git 托管引擎。创建平台项目只建立平台记录及关联，不自动创建、迁移、镜像或复制远端仓库。成员授权并选择仓库后，即可在平台内查看其代码、Issue 与 PR；私有仓库无需改为公开。

可关联的仓库必须处于连接的授权范围内，成员访问同时受第 2 章的平台角色及仓库关联约束。连接授权不等于向所有访问者公开私有代码，也不改变现有开发者与浏览者角色。浏览者保持只读，客户反馈入口不获得代码访问权限。授权失效、撤销或移除仓库访问权限后，平台应停止提供该仓库的受保护内容，包括缓存内容，并显示访问不可用及恢复授权入口。

代码查看不要求用户手动同步。后端按需获取目录和文件，可结合缓存与后台自动更新；全仓克隆不是阅读文件的前置条件。切换分支后必须读取对应版本，无法访问、文件不存在和请求失败不得伪装为空目录。Bot 的代码修改、创建 PR／MR 等写操作通过第 10.7 节的项目能力执行。原型仅模拟写入本地状态，尚未连接远端。

开发过程采用“人工状态加 Git 关联”的方式：负责人维护业务进度，代码记录提供进展依据。代码提交、合并记录不替代成员对业务状态的维护。

项目页面应能查看 PRD 执行人和开发过程，并汇总服务的交付信息。服务可以独立交付，版本展示规则见第 8 章。

Git 托管平台是代码、提交、PR 及远端 Issue 原生信息的权威来源。平台维护 PRD、内部 Bug、业务流转及其代码关联。PR 合并、Issue 关闭不会自动标记测试通过或已发布。

## 5. PRD 与研发流程

PRD 同时支持在平台内编写和关联外部文档。产品指派研发主负责人，主负责人可以与多名研发协作；进入测试环节时指定测试负责人。

平台记录以下业务过程。表中的环节用于描述工作流，不是已经确定的状态枚举，也不表示每个环节都必须增加审批动作。

| 环节 | 主要参与者 | 需要记录的业务内容 |
| --- | --- | --- |
| 提出需求、指派研发 | 产品 | 需求内容、研发主负责人和协作人员 |
| 技术调查 | 研发 | 调查结论；简单需求可直接通过 |
| 开发 | 研发 | 开发进度、关联代码与讨论 |
| 自测、准备提测 | 研发 | 自测、单元测试情况，以及可供测试的交付信息 |
| 提测 | 研发 | 业务状态流转、测试负责人 |
| 测试 | 测试人员 | 按 PRD 验证功能，提出 Bug 清单 |
| 修复 | 研发 | 处理测试发现的问题，记录修复进度 |
| 回归测试 | 测试人员 | 验证修复结果，未通过的问题继续修复 |
| 正式交付 | 相关负责人员 | 人工放行后上线或提审，记录交付结果 |

研发自测时可以通过平台内置流水线准备可安装测试包，或将服务部署到测试环境；流水线定义在代码仓库中以 YAML 文件维护，由平台执行节点运行。平台在业务流程中记录提测，不负责通过该状态动作执行上述工作。

开发完成、测试通过和已发布是不同的业务结果；提交外部审核也不等于已经发布。具体完成判定及状态取值列入第 12 章。

## 6. 流水线、执行节点与提测的独立边界

平台内置流水线。流水线定义保存在代码仓库的 YAML 文件中，格式参考 GitHub Actions 与 Gitea Actions 的工作流文件；平台读取当前分支或提交上的定义，在注册到平台的自托管执行节点上使用隔离容器执行。平台拥有定义解析、触发、运行编排、状态、日志、产物与审计，不调用 GitHub Actions、Gitea Actions 等第三方流水线 API。

| 对象 | 职责归属 | 与其他流程的关系 |
| --- | --- | --- |
| PRD 与提测状态 | 产品、研发、测试维护业务过程 | 不负责触发、等待或重试流水线 |
| 项目流水线定义 | 研发在代码仓库的 YAML 文件中维护，随代码评审 | 平台只解析与执行，不提供绕过代码评审的线上编辑 |
| 流水线运行与执行节点 | 平台编排，平台注册的自托管节点执行 | 独立决定何时构建、部署和产生结果 |
| 产物收集与展示 | 平台 | 接收并展示可供使用的交付结果，不据此自动推进 PRD |
| 运维变更 | 平台计划与授权，执行节点或外部执行系统执行 | 单独创建操作，追踪执行和验证结果，与提测解耦 |

以下规则约束产品设计和后续实现：

- 点击“提测”只改变业务状态，不自动触发构建、上传或部署。
- 提测不以某条流水线执行完成为强制前提。
- 流水线成功或失败不自动修改 PRD 状态，也不自动生成提测动作。
- 不以“构建失败”为由自动回退 PRD，或要求通过修改 PRD 状态重试流水线。
- 生产影响的操作必须通过变更计划确认并人工放行；通过任务验收不会自动批准发布。
- 执行节点离线、任务超时或来源代码不可访问时保留任务与错误，不能显示执行成功。

第一版流水线支持手动触发，以及项目、节点与单条流水线的并发限制；自动触发（如 push、标签、定时）在后续版本评估，且不得与提测等业务状态产生隐式联动。

## 7. 构建产物与测试交付

测试人员最终需要拿到可使用的测试版本。平台集中收集和展示以下交付内容，使成员能够找到构建结果和测试入口。

| 类型 | 最终交付内容 | 使用方式 |
| --- | --- | --- |
| 移动端应用 | 可安装的测试包 | 下载并安装 |
| 小程序 | 测试二维码 | 扫码体验 |
| Web／后端 | 测试环境访问地址及交付信息 | 访问页面或验证接口 |

产物的生成、签名和上传由平台内置流水线的运行过程或研发本地交付过程完成。测试环境部署可以由平台流水线的部署步骤执行，也可以由独立的运维变更计划调用执行节点或已接入的外部执行系统；两者都必须回传实际结果。展示二维码不承担小程序上传。

平台展示最新构建产物，并提供对应的版本信息。收集是否采用主动上报、拉取结果或其他方式，以及平台保存文件还是仅保存引用，均列入第 12 章。

## 8. 服务版本与交付结果

各服务分别展示运行版本，允许独立发布。成员应能按服务和环境了解当前上线版本，同时查看可用的构建产物。“产物与版本”页面不单独展示交付记录列表或发布放行卡片；保留产物与运行版本的来源信息，以便核对交付结果。

最新构建产物与环境正在运行的版本需要分开展示。构建完成不代表该产物已经部署，也不能用最新构建记录直接替代线上版本信息。

第一版不要求统一的产品发布版本来绑定所有服务。运行版本的权威来源、交付记录的采集方式和版本标识规则列入第 12 章。

## 9. Bug、发布与外部审核

客户和内部人员都可以提交 Bug，在项目内统一处理。测试人员可根据 PRD 提出 Bug 清单，研发记录修复过程，测试人员记录回归结果；回归未通过的问题继续修复。

Git 平台中的 Bug 通常由 Issue 及其分类表示，需要约定标签或类型映射。平台不能仅凭读取代码自动获得 Bug 清单。平台本地 Bug 与外部 Issue 的关联方案见第 11 章；客户反馈入口不要求客户取得代码仓库权限。外部 Issue 的开关状态与本平台的修复、回归状态分别展示，避免同名字段覆盖不同含义。

正式发布需要人工放行。Leader 准备版本、环境、范围、核对依据和恢复方案，由成员确认具体计划。操作经历待确认、已批准、执行中、待验证和已完成；失败单独记录，重试前核对外部执行状态，避免重复操作。执行成功后仍需验证服务健康及实际运行版本。部署、数据库变更、服务器清理和云资源调整共用此操作框架，具体执行连接器尚未接入。

小程序和移动端应用的外部提审属于第一版范围。成员使用研发交付的产物，在外部平台人工提交审核；本平台记录审核与实际发布结果。平台不自动向外部平台提交审核，审核状态如何维护或同步列入第 12 章。

## 10. Bot、团队 Skills 与协作模板

### 10.1 独立 Bots、会话与项目入口

Bot 是团队中独立存在的智能体，保存名称、头像、职责、负责人、运行环境、模型与技能配置。创建 Bot 不必绑定项目；一个 Bot 可以处理通用工作，也可以获准操作多个项目。全局管理保留表格、搜索、负责人筛选、配置和启停，点击 Bot 即可进入直接会话。

协作采用会话列表、聊天正文和可收起的右侧面板。支持与单个 Bot 对话，以及包含多个 Bot 的群组；创建会话填写名称、成员和 Leader，可补充职责与指令。点击群名或设置按钮展开会话设置，集中维护成员、Leader、职责、指令、工作标签及项目工具引用；任务面板与设置面板互斥展示。主聊天区保留消息、折叠的任务与工具活动，以及底部输入框，加号菜单承载附加操作。

工作标签是独立分类，例如“身份与权限”“发布交付”，可关联零个、一个或多个项目。项目相关性仅按标签判断：会话本身或其中任务带有归属于当前项目的标签，该会话才进入项目协作页。资源引用、群名及任务的目标项目本身不作为归集条件。项目内直接展示相关聊天和 Bots 群组及原消息记录，不设置“全部标签”筛选，不允许新建会话、发送消息或管理标签。

Bot 在任务成功交付后整理标签，优先复用合适的分类，没有合适分类时新建，并关联任务涉及的项目；失败结果不自动归档，重复验收不重复创建标签。人也可以在会话设置中创建或选择标签，编辑名称及项目归属。标签关联变化即时影响项目归集，移除关联不会删除原聊天或任务。原型以本地关键词规则模拟 Bot 分类，尚未接入 Agent 语义分类。

标签只负责归类，不授予资源访问权限。跨项目会话必须明确可见成员和资源访问范围，不能因为关联到项目就向全部项目成员公开原私聊；正式服务查询需要同时满足标签匹配与当前用户的会话可见权限。

Leader 是群组内默认承接目标、分派和汇总的成员，不是更高权限角色。未指定执行者时由 Leader 承接；明确 `@Bot` 时交给该 Bot。更换 Leader 不自动改写已有任务分工。群成员、项目引用和项目工具授权分别配置：加入群组不获得项目权限，引用项目不授予写权限，移出群组不删除 Bot 的独立身份或其他项目授权。移出成员后，仍由其执行的未完成工作应阻塞并等待重新分派。

聊天默认直接发送消息，不把每次发言自动转换为任务。用户消息使用右侧气泡，Bot 回复使用左侧头像和正文；时间弱化，任务和工具活动默认折叠。新建任务通过明确的“新任务”或输入框加号菜单操作；选中未完成任务后可切换“补充当前任务”，追加要求并保留已有结果。任务保存业务负责人、当前执行者、来源、交接记录和可选目标项目。通用任务可以提交文本结果，不要求分支、Commit 或构建产物。涉及代码开发时记录开发交付，发布计划单独发起。每个任务有一位当前执行者，转交不丢失历史；第一版不要求无限递归分派或群内所有 Bot 自动轮流发言。

全局停用、项目工具授权撤销和运行环境离线分别表达。新运行检查当前会话成员与执行者可用性；每次项目调用另外检查目标项目和具体能力。成员之间不合并权限，Leader 不能替其他 Bot 授权。私聊、群聊及项目记录各自维护可见范围，不能仅靠前端筛选保护信息。

资源通过输入区 `@` 搜索，候选区分 Bot、项目、文件、PR、事项和 Skill。项目上下文限制候选范围；被选执行者仍需拥有对应读取权限。跨项目引用保留项目标识，未知、失效或无权限引用提供错误反馈，不静默改为其他资源。原型示例包括 `@project/dev-ops`、`@repo/team/dev-ops`、`@file/src/api.ts`、`@pr/42`、`@PRD-024`、`@小李`、`@skill/pr-review`；完整协议、实例及多仓库消歧仍需技术设计。

工具入口与 `@` 引用使用同一套项目能力。调用前呈现执行者、目标项目、工具及输入；结果保留在原会话，并可打开对应项目记录。生产部署、数据库写入及删除等操作通过具体变更计划授权，环境凭据按第 10.6 节独立控制。长期工作由平台任务与执行系统维持，不依赖浏览器一直打开。

Grok Bot 是角色、群聊和对话体验的参考。本机安装的 OpenBot 已确认是 `nightly-labs/openbot` 0.59.0（2026-11-07 检查应用包元数据）；其[公开说明](https://github.com/nightly-labs/openbot)中的独立智能体、持续会话、任务排队、交接与上下文压缩用于交互研究。本项目未引入其执行代码，也未实现完整功能对齐；调度、记忆压缩和真实 Agent 运行仍需另行实现。

### 10.2 团队 Skills 平台

Skills 是团队技能的统一目录与管理入口，采用技能市场式浏览方式。目录支持按名称、调用标识和分类检索；技能详情展示用途、版本、来源、指令内容和启用状态。团队成员可以发布、编辑、启用或停用技能，权限遵循第 2 章。

Bot 使用团队已启用且自身配置允许的技能。技能提供工作方法，不授予项目工具或密钥权限；执行时仍按目标资源检查授权。成员既可以在技能详情选择“在 bots 中使用”，也可以在对话输入区通过 `@` 搜索 Skill。两个入口引用同一份技能定义，不复制维护。停用技能应从新调用候选中移除；手工输入已停用的标识也不能继续调用。历史对话中的调用信息仍可用于追溯。

团队技能平台不等于必须接入公开第三方市场。第三方来源导入、版本更新、审查和分发方式仍待确认，当前原型以团队维护的技能为示例。

### 10.3 AGENTS.md 模板

Skills 中提供独立的 `AGENTS.md 模板` 目录，支持新建、编辑、创建副本、搜索、查看全文、复制正文、下载文件、复制预览链接，以及明确选择目标项目后选用模板。预览链接应呈现分享时的内容版本；原型使用同站点快照链接，公网发布、访问权限和撤回机制需另行确定。Bot 操作该项目时使用所选模板作为协作约定；同一团队的不同项目可以选用不同模板。模板选择不应直接写入或覆盖远端仓库中的 `AGENTS.md`。

上下文和技能沿用“团队共用，加项目专属”的组织方式。团队维护通用能力，项目补充自身资料和约定；不恢复独立“上下文”页签。模板与仓库已有规则的合并顺序、项目覆盖、版本锁定及生效时机列入第 12 章。原型展示模板选择及调用信息，不代表模型、执行器或远端文件写入已经接入。

### 10.4 值守、事件与通知

运维用于处理运行中的服务问题和服务变更。通过运行事件区域的“演示一次日志异常”入口串联告警、Bug、Bot 排查任务、开发交付、验收、变更计划及发布验证。事件详情可查看证据并返回同一 Bug 和会话；不把运维作为只有版本数字的展示页。

值守规则绑定项目、环境、Bot、触发条件与启停状态。日志采集系统先聚合前后端异常，Bot 按事件和所需片段分析，不把所有原始日志持续塞入对话。相同错误在约定窗口内聚合到同一问题，保留次数、时间和证据；新问题建立平台 Bug 及处理任务，并由 Leader 组织跟进。远端 Issue 创建使用另行授权的适配器，不能把本地建单展示成远端创建成功。

磁盘巡检可以生成清理建议，实际清理需指定资源、目录、保留规则和恢复办法。规则支持暂停，执行节点离线时显示阻塞，不静默丢弃任务。定时调度、失败退避、重复事件去重和中断恢复属于正式执行系统需求；原型仅提供手动演示触发。

通知中心收集阻塞、配置请求、待验收和发布结果。飞书承担外部通知与返回平台的入口；发布计划应包含明确版本与环境，通知不另建一套任务状态。原型只预览通知，不实际发送。

### 10.5 开发交接与记忆

平台提供统一 CLI/API 供 Codex、Claude、pi 和人工开发使用。代码开发交付关联项目、任务、分支、提交、测试结果和说明，涉及构建时附产物；通用任务只要求结果及必要证据。Hook 可自动触发上报，手工开发也可主动上报。Git 事件和 CI 结果用于补充核对。不能依赖工具 Hook 覆盖所有变更，也不能假设手改一定很小；未关联的提交应可被识别并补充关联。无需同步完整聊天记录或所有本地操作。

记忆由平台维护，区分 Bot 身份、项目约定与任务交接摘要。会话上下文可以压缩，长期知识需保留来源、范围、确认状态，并允许查看、修正和删除。版本、授权及任务状态始终读取业务记录，不能仅凭记忆中的旧值决定操作。密钥明文不进入记忆。原型提供项目与 Bot 维度的手工记忆管理，尚未实现自动提取与检索。

### 10.6 环境变量与密钥

团队凭据库参考密码管理器的目录与详情布局，统一管理 API 密钥、账号密码和 SSH 密钥，支持检索、分类、配置请求、管理员编辑、轮换和撤销。对外名称为“凭据库”。配置请求与使用、管理记录收在右下角的小日志箱中，默认只显示图标，有待配置请求时显示数量。点击后打开独立大弹窗，支持按配置请求、管理记录筛选，长列表在弹窗内部滚动，不占正文行；凭据目录和详情填满可用高度，不重复显示页面大标题和说明。

团队管理员指定凭据允许的项目、Bot 和期限；项目环境保存凭据引用及变量名，不复制密钥。引用不能扩大团队授权。复制引用只产生资源标识，不包含密钥，也不构成公开下载地址。轮换保持引用标识并更新版本；撤销、缩小授权或过期后阻止后续使用，依赖任务等待重新配置。本版本管理员与开发者可在凭据详情输入本人登录密码后临时查看当前版本明文，默认 30 秒后自动隐藏，查看动作写入审计；API Token、浏览者和外团队不能代替密码确认。除该查看入口外，产品仍不提供明文复制、下载或批量导出。

项目提供开发、测试、生产等环境配置，环境间不自动继承密钥。同一项目与环境内名称唯一，区分普通变量与密钥，展示是否配置、版本、授权方式和允许使用的 Bot。密钥默认遮蔽；复制、下载和公开链接不适用于密钥，AGENTS.md 与 Skill 中只保存引用名称。

使用方式分为运行时注入与允许 Bot 读取明文。运行时注入由执行器解析引用，模型与聊天不接触值；明确允许明文读取时也只对指定 Bot、项目、环境及授权期限生效。期限支持当前任务、限时或长期；平台管理权限不等于对所有 Bot 的读取授权。正式实现应对每次使用检查当前授权，记录使用者、任务、版本及结果，日志不记录值。

Bot 可以提出缺失配置请求、建议名称、用途和目标环境，或在授权工具支持时申请创建、轮换凭据。用户在独立表单中配置值和允许对象，任务等待配置；授权满足且执行者可用后继续。密钥创建不能通过聊天伪造成功，无法自动签发的凭据应交由用户配置。撤销或过期后禁止新的使用，依赖该授权的任务进入等待配置；已有运行中的凭据如何失效由执行系统明确处理。

正式产品将密钥存入加密凭据服务，优先支持云角色或短期凭据；具体服务和连接器仍待技术选型。原型只保存密钥名称、版本、授权范围和状态，不保存、回显或发送输入的测试密钥。普通变量保存在浏览器本地，真实敏感值不得当作普通变量录入。

### 10.7 项目能力与调用结果

项目对 Bot、CLI 和界面开放一致的业务能力。以下名称用于说明产品边界，尚未确定为真实 API。服务端必须校验操作者、Bot、项目、具体操作和资源归属，不能将聊天中的 `@`、技能指令或前端按钮视为授权凭证。

| 能力 | 输入与行为 | 输出与边界 |
| --- | --- | --- |
| 读取项目 | 项目、仓库、分支及资源引用 | 读取已授权内容；缓存不能绕过撤销 |
| 修改代码 | 项目、工作分支、文件、修改目标 | 在执行环境产生变更、差异及验证结果；不隐式覆盖默认分支 |
| 调用流水线 | 项目、仓库内工作流定义、分支或提交和参数 | 返回运行标识、状态和日志；按项目能力授权，提测及业务进度保持独立 |
| 更新项目进度 | 项目、事项、状态和说明 | 更新同一业务记录并保留活动历史 |
| 提交 Bug | 项目、标题、复现与证据 | 建立平台 Bug；创建远端 Issue 是另一项明确的同步动作 |
| 提交 PR／MR | 项目、仓库、源分支、目标分支及说明 | 返回远端记录或明确失败；不自动合并、发布或标记需求完成 |
| 添加评论 | 项目、事项或远端记录、正文 | 在指定目标下添加评论并回传引用；远端评论单独校验连接权限 |

项目能力按 Bot 与项目授权，写能力明确选择，默认不从旧的读取授权推导。一次工具调用必须有一个明确目标项目；跨项目任务拆为分别授权、分别记录结果的调用。调用授权不等于运行时凭据授权，密钥仍通过独立配置流程提供。

记录每次调用的发起会话、执行者、目标、输入摘要、执行状态和结果引用。重试遵循具体工具的幂等规则，异步操作记录运行标识，取消不声称撤销已经发生的写入。权限撤销后禁止后续调用，已经启动的外部任务按执行器能力停止或报告仍在运行；不得伪造成功。

当前原型可演示上述七类调用，结果与代码页、Bug／需求、PR 和流水线页面共享本地状态。代码修改仅保存本地工作分支示例；PR／MR 为本地草稿；流水线通过手动按钮模拟完成。模型自动选择工具、远端提交、真实流水线和外部评论均未接入。

## 11. 接入方案与待确认建议

### 11.1 GitHub 与 Gitea 适配

API 接入方式与私有仓库支持已确定，产品范围见第 4 章。第一版包含仓库信息、分支、目录、文件、提交、Issue 与 PR 的读取和关联，并按第 10.7 节提供授权写能力；具体认证权限、适配接口和失败恢复列入第 12 章。GitHub 与 Gitea 使用统一的页面交互，保留来源平台及实例标识，便于成员定位原始记录。

不同 Gitea 实例中的同名仓库或相同 Issue／PR 编号不得混淆。平台不承诺两边能力完全一致；不支持、无权限、请求失败和同步延迟需要明确展示，不能转换为空列表或成功状态。

流水线由平台内置，遵守第 6 章；GitHub 与 Gitea 只作为代码与 PR 来源，平台不调用其 Actions 或 Workflow API。流水线定义参考两边工作流文件的写法，但执行语义由平台定义，不承诺与 GitHub Actions 或 Gitea Actions 完全兼容；不支持的语法必须在解析时明确报错。产物与交付结果的采集方式仍按第 12 章确认。

认证方案、适配器职责、缓存与事件同步约束及官方能力依据统一维护在[技术选型第 4.1 节](../architecture/server-foundation.md#41-代码平台-api-接入)。本节确定的产品要求不代表真实连接已实现或通过验证。

### 11.2 Bug 与外部 Issue

建议平台维护客户与内部 Bug，并按需关联已有 Issue，提供单独授权的远端 Issue 创建动作。GitHub／Gitea 原生标题、标签及关闭状态从来源读取，本平台的业务状态由本平台维护。若需要双向修改同一字段，必须先确定权威来源、冲突处理及重试规则；不默认启用全量双向同步。

这会增加关联管理成本，但能保留客户反馈入口及回归流程。仅使用远端 Issue 可减少本地业务数据，是否满足客户权限和测试流程要求仍需产品确认。

### 11.3 需求与产物关联

建议允许 PRD 或 Bug 关联已有产物，便于成员知道测试的是哪个版本，并在排查问题时追溯交付结果。这种关联应保持第 6 章的独立边界，不触发流水线执行。

关联是否存在、是否必填、是否固定到某次构建，以及是否引入独立测试轮次，都需要产品负责人确认。自动提测、构建失败重试、测试轮次及其通知规则不作为已确认功能。

## 13. 需求核对场景

以下是后续设计与实现的验收依据，不表示当前代码已通过对应功能测试。

- 一级导航顺序为项目、协作、运维、能力、凭据库；能力包含 Bot、Skills、模板、记忆及连接配置。
- 普通消息不自动创建任务；任务与工具活动可折叠，任务通过显式操作创建。
- 管理员可管理团队资料、邀请、角色与成员停用；开发者、浏览者不能修改团队管理项，不能移除最后一位管理员。
- root 可通过真实邮件邀请团队管理员，团队管理员再邀请成员；首次受邀者设置密码、补全所需资料并进入首页，之后使用邮箱和密码登录。
- 多团队切换位于侧栏最底部，只有一个团队时隐藏；图标保持正方形，切换后会话和凭据隔离。
- 团队凭据只保存授权引用到项目环境，轮换同步版本，撤销阻止后续使用；管理员/开发者输入本人密码后可临时查看当前版本明文；配置请求和管理记录收在右下角日志入口的大弹窗。
- 默认首页进入全局协作；项目默认进入需求，需求位于首位。项目协作直接展示按标签匹配的聊天和 Bots 群组及消息，不提供标签筛选、新建或发送入口。
- 需求可按文字、状态和负责人组合筛选，空结果可恢复；点击事项打开右侧详情，关闭后保留筛选条件。
- 已授权的已有 GitHub 或 Gitea 仓库可以关联到项目，无需另建仓库或由成员手动同步；文件查看读取当前分支，错误可见且可重试。
- GitHub 与 Gitea 分别使用公有、私有仓库验证读取和关联；私有仓库保持私有，未授权仓库不能关联或读取。
- 撤销授权或移除仓库权限后，按确定的检测时限停止返回受保护内容，缓存不能绕过权限检查；恢复授权后可重试读取。
- 不同 Gitea 实例中的同名仓库、相同 Issue／PR 编号分别展示；不支持的能力与请求失败不会被展示为成功或空数据。
- 代码、PR 和远端 Issue 的读取不自动改变平台业务状态；本地 Bug 与远端 Issue 按确定的映射方案处理。
- 一个项目可以展示多个服务，各服务分别呈现环境运行版本和最新构建产物，两者不会混为同一个版本。
- 产品能够创建内置 PRD 或关联外部文档，并指定研发主负责人、协作人员；提测时可指定测试负责人。
- PRD 可记录第 5 章所述业务过程，测试人员可以提交 Bug，研发与测试可以记录修复、回归结果。
- 没有正在运行的流水线时仍可以改变提测状态；该操作不会创建构建或部署任务。
- 平台内置流水线产生新产物、运行成功或失败时，不会自动变更 PRD 状态。
- 平台可以读取仓库内 YAML 定义的流水线，在注册的执行节点上运行并保存日志、产物与运行记录；节点离线或语法不支持时显式失败，不显示为成功。
- 测试人员可以获取第 7 章对应类型的交付入口；正式发布和外部审核结果能够与构建完成分别表达。
- 客户和内部人员均有提交 Bug 的方式；管理员管理团队及凭据，开发者管理业务，浏览者保持只读。
- 成员可从事项详情建立 Bot 任务，或在项目会话用 `@` 选择执行者，其能力受项目授权约束。
- 全局 Bot 支持独立创建、搜索、负责人筛选、配置、启停和项目能力授权；无需选择项目即可私聊、建群、提交通用结果。项目协作按标签展示同一会话，项目资源引用本身不触发归集。
- 会话可引用多个项目；添加上下文、修改成员或更换 Leader 均不扩大工具权限。移出当前执行者后任务受阻，转交只能选择当前会话成员。
- 七类项目工具分别校验目标和权限，工具结果可回到对应项目记录；失败、离线、权限撤销不显示为成功。
- 项目 bots 不展示助手卡片和 Git 摘要栏；输入 `@` 可选择资源及团队技能，未知、失效或无权限的引用不会被执行。
- Skills 支持搜索、分类、查看定义及管理启用状态；技能库入口与 bots 引用同一技能定义。
- AGENTS.md 模板可预览并按项目选用，选择结果在项目 bots 中可见，不自动改写远端仓库。
- 产物与版本页面只展示产物及环境版本，不单列交付记录或发布放行卡片。

- 重复日志事件聚合到已有问题；规则暂停或执行者离线时不能宣称正常执行。
- 配置请求包含项目、环境、用途及 Bot；撤销、过期、跨环境或跨任务的授权不能继续使用。
- 输入测试密钥后原型仅保存元数据，提交和取消表单后清除输入值。
- 开发结果进入待验收，验收不自动发布；部署计划经确认、执行及验证后更新运行版本。
- 手工开发与工具开发使用同一交付入口，Hook 缺失不能导致变更永远不可见。
- 记忆保留来源和范围，可修订、删除；密钥不进入对话记忆。

## 补充：V0.4b 交付口径（2026-11-11）
